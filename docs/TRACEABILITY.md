# Threat → requirement → mechanism → test → evidence (proposal Appendix A)

Status of each row is stated plainly: **covered** (mechanism built and tested), **partly covered** (a gap is named), or
**boundary documented** (deliberately not addressed).

| Threat | Requirement | Mechanism in this repository | Tests | Retained evidence | Status |
|---|---|---|---|---|---|
| **T-01** HNDL of recorded traffic | R-01 Use hybrid key establishment on the supported target path; label fallback as classical exposure | Sidecar negotiates `X25519MLKEM768` and verifies the group from the ServerHello; classical negotiation is allowed only for explicitly `classical-allowed` peers and is recorded as `allowed-fallback`; the console and each partner transaction show hybrid vs classical | `pqc-sidecar/tests/{wire,sidecar,scenarios}.test.ts`; `security-service/tests/hndl.test.ts` (simulator); `moneypurse-web/tests/lib/provenance.test.ts` | `evidence/e2e/*/results.json` (live handshakes, group, key-share sizes); `evidence/bench/*` (wire bytes); simulator runs stored in `hndl_runs` | **Partly covered:** no pcap is retained, the verified handshake trace stands in for it (proposal 8.1); protection ends at the sidecar |
| **T-02** Long-term key compromise | R-02 Avoid exposing ephemeral secret material; document lifetime assumptions | TLS library key schedule with ephemeral key agreement; keys never logged (`redact` plus no header logging); peer private keys exist only in the simulator process and never in the security-service or repository | `ledger-service/tests/http/log-hygiene.test.ts`, `security-service/tests/log-hygiene.test.ts` (negative tests for secrets in logs, mutation-checked); CBOM key-file refusal tests | CBOM `sourceSummary.refused` lists any file refused because it looked like key material | **Covered for the exercised paths;** key storage and rotation assumptions are documented in `PROJECT_STATUS.md` section 5 only, no key-rotation mechanism exists |
| **T-03** Downgrade or policy violation | R-03 Enforce the expected peer profile: reject or alert, with a timestamped event | Peer registry (certificate fingerprint → profile), policy evaluator, one decision per connection, severity derived server-side, alerts with acknowledgement | `pqc-sidecar/tests/{policy,scenarios}.test.ts` (hybrid-required offered classical, unknown peer, untrusted certificate, no certificate, controlled ClientHello modification); `security-service/tests/{peers,telemetry}.test.ts` | e2e section 3 and 6 (all five decisions observed live); connection event log | **Covered** within the stated visibility limit: a stripped ClientHello is indistinguishable from a classical client (scenario `clienthello-downgrade-tamper`) |
| **T-04** Insider or database compromise | R-04 Limit sensitive data in the audit store and validate changes | Four roles with a permission matrix, per-service least privilege, separate databases for banking data and security events, zod validation on every input, append-only hash-chained audit with DB triggers, configuration changes transactional with their audit entry | `ledger-service/tests/http/rbac.test.ts`, `security-service/tests/{access,audit,config}.test.ts`, log-hygiene tests | e2e sections 2 and 7 (role matrix, both audit chains verify) | **Covered;** a database superuser can bypass the triggers (verification then reports the break) and tail truncation needs an external head hash |
| **T-05** Cryptographic supply-chain risk | R-05 Record versions and approved provider source; verify provenance and checksums where available | `package-lock.json` pins dependencies with npm integrity hashes; the benchmark manifest records Node, OpenSSL, CPU, OS, commit and dirty flag; the CBOM scans dependency manifests for cryptographic libraries; evidence files carry SHA-256 checksums and are kept byte-exact (`.gitattributes`) | `pqc-sidecar/tests/bench.test.ts` (manifest), `security-service/tests/cbom.test.ts` (dependency scan, schema hash check) | `evidence/bench/*/manifest.json`, `checksums.sha256`; CBOM documents | **Partly covered:** no signature or provenance verification of npm packages beyond lockfile integrity; no reproducible-build check; OpenSSL version is whatever the Node binary embeds |
| **T-06** Future compromise of classical or PQ signatures | R-06 Avoid implying PQ authentication; state that certificates remain classical | Certificates are ECDSA P-256 and tokens EdDSA; the CBOM inventories them as classical; every status entry, the console notice and the claim ledger state the boundary | `security-service/tests/{status,cbom}.test.ts` (no restricted claim language, certificates inventoried as classical); `node scripts/claim-audit.mjs` | CBOM certificate assets; claim ledger section 3 | **Boundary documented:** no PQ signatures, PKI migration or JWT migration (out of scope, proposal section 21) |
